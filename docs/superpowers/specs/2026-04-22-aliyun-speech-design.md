# Jarvis 阿里云语音替换设计文档

## 1. 问题与目标

当前 Jarvis 的语音链路依赖 Azure Speech：

- `AzureAsrService` 负责语音识别
- `AzureTtsService` 负责语音合成
- `SpeechService` 负责把 ASR、Kimi、TTS 串起来

现状问题是 Azure Speech 的接入和配置成本偏高，不利于快速完成真实联调与长期使用。

本次目标是把 Jarvis 的语音主路径改为 **阿里云 DashScope**，并满足以下要求：

1. 语音识别（ASR）改为阿里云。
2. 语音合成（TTS）改为阿里云。
3. 前端语音交互入口、WebSocket 协议、Kimi 对话链保持不变。
4. 配置中心的语音配置项改为阿里云优先。
5. 健康检查、运行时配置检测、错误提示不再默认指向 Azure。
6. 主控台补上左右侧栏收起能力，并改成更聚焦、更有 Jarvis 控制台感的视觉布局。

## 2. 非目标

本次不包含以下内容：

- 不实现多语音 Provider 抽象层。
- 不保留 Azure 与阿里云并存切换能力。
- 不重做实时网关协议。
- 不重写前后端通信协议。

本次采用最短路径，直接把 Azure 主链路替换为阿里云实现，同时对主控台做一次视觉收口。

## 3. 方案选择

已确认采用：

- **方案 2：直接替换 Azure**

原因：

- 实现最短。
- 当前目标是先把真实语音链路跑通。
- 不增加额外抽象层，避免继续扩大改动面。

代价：

- 后续如果还要重新支持 Azure，需要再补回 Provider 抽象。

## 4. 总体设计

### 4.1 服务替换

现有语音服务结构保持不变，但底层实现替换：

- `AzureAsrService` → `AliyunAsrService`
- `AzureTtsService` → `AliyunTtsService`
- `SpeechService` 继续作为统一编排入口

`SpeechService` 的对外行为不变：

- 输入音频
- 调用 ASR 获得转写
- 调用 Kimi 生成回复
- 调用 TTS 合成音频
- 返回转写文本、回复文本、音频字节和 MIME 类型

这样可以保证上层路由、前端语音球、WebSocket 事件、回放逻辑不需要重写。

### 4.2 配置模型

后端配置改为阿里云字段，默认由 `.env` 和运行时配置中心提供：

- `ALIYUN_DASHSCOPE_API_KEY`
- `ALIYUN_ASR_MODEL`
- `ALIYUN_TTS_MODEL`
- `ALIYUN_TTS_VOICE`
- `ALIYUN_SPEECH_LANGUAGE`

默认约束：

- ASR 与 TTS 共用同一个 DashScope API Key。
- 默认语言为 `zh-CN`。
- 默认音色使用一个稳定中文音色，具体值在实现时固定为可用的 DashScope 中文音色。

原有 `AZURE_SPEECH_*` 不再作为主路径依赖，也不再作为健康检查的必填项。

### 4.3 运行时配置中心

前端“服务与模型配置”中的语音区域改为显示阿里云字段：

- DashScope API Key
- ASR 模型
- TTS 模型
- 音色

运行时检测逻辑改为：

- Key 存在时，`speech` 至少视为已配置
- 如果后端提供语音检测接口，则按阿里云字段进行检测

前端文案统一改成“阿里云语音”或“语音服务”，不再引导用户填写 Azure Key / Region。

### 4.4 主控台布局收口

主控台默认改成“**主区聚焦，侧栏按需展开**”：

- 左侧栏默认收起
- 右侧栏默认收起
- 两侧都通过悬浮入口按钮展开
- 展开方式为覆盖式抽屉，而不是长期占据布局宽度

页面默认只保留以下核心区域：

- 顶部状态条
- 中央主对话 / 主工作区
- 底部命令坞
- 少量悬浮操作入口

配置、任务、记录、资料上传等次级内容收进抽屉或二级面板，不在首页同时摊开。

### 4.5 视觉风格收口

视觉方向调整为更强的 Jarvis 控制台风格：

- 使用更统一的深色背景和高亮色
- 明确主次层级，减少同时可见卡片数量
- 强化状态灯、边框光效和 HUD 感
- 保证默认打开时页面简洁，不显得拥挤和杂乱

目标不是增加更多组件，而是通过默认折叠、层级减法和状态聚焦，让主界面更像“驾驶舱”。

## 5. 数据流

语音闭环仍保持 5 段式流程：

1. 前端采集音频并发给后端。
2. 后端用 `AliyunAsrService` 识别文字。
3. `SpeechService` 把文字交给 Kimi。
4. 后端用 `AliyunTtsService` 合成回复音频。
5. 前端播放音频并展示文本。

数据结构不变：

- `transcript`
- `reply_text`
- `audio_text`
- `audio_bytes`
- `audio_mime_type`

这样可以最大限度复用当前测试、前端回放和状态管理逻辑。

## 6. 错误处理

错误处理改为阿里云语义：

- 未配置 Key：返回“阿里云语音未配置”
- ASR 失败：返回“阿里云语音识别失败”
- TTS 失败：返回“阿里云语音合成失败”

健康检查和配置检测规则调整为：

- `speech=missing`：缺少 DashScope API Key 或必要模型参数
- `speech=configured`：阿里云语音基本配置齐全

文本聊天链路不受语音失败影响。

## 7. 测试与验收

### 7.1 后端

需要补充或更新以下测试：

- 阿里云 ASR 配置缺失时抛出明确错误
- 阿里云 TTS 配置缺失时抛出明确错误
- `SpeechService` 使用阿里云实现后仍能返回既有结果结构
- 健康检查中的 `speech` 状态依据阿里云字段判断

### 7.2 前端

需要更新以下断言：

- 配置中心语音字段改成阿里云字段
- 受限态不再提示用户启动 Azure Speech
- 左右侧栏默认收起
- 点击入口后以覆盖式抽屉展开
- 主界面默认可见模块数量减少，但核心交互仍可直达

### 7.3 真实验收

真实验收通过标准：

1. 填入 DashScope API Key 后，配置中心可保存并重新加载。
2. 点击语音相关操作时，不再因为 Azure 缺失而报错。
3. 完成一次真实语音闭环：录音 → 转写 → Kimi 回复 → 语音播报。
4. 主界面不再要求用户填写 Azure Key / Region。
5. 页面默认打开时左右侧栏处于收起态。
6. 展开侧栏时使用覆盖式抽屉，不把主内容区长期挤窄。
7. 主界面视觉更聚焦，默认不再出现“信息堆满一屏”的观感。

## 8. 实施边界

本次只做“阿里云替换 Azure”的收口，不顺带做以下扩展：

- 语音供应商统一抽象
- 多供应商切换 UI
- 实时流式 TTS 优化
- VAD 策略重构
- 完整重写整套设计语言系统

如果后续需要支持多家语音服务，再基于本次阿里云实现补一层抽象。
